# Requirement Traceability Matrix

> **Purpose:** Trace every requirement through Design, Code, Test and runtime Monitor, so that any requirement can be followed forward to its evidence at any time.
> **Authoritative for:** the links between artifacts. Requirement content, type and status come from `docs/req/requirements.yaml`; if a cell here disagrees with it, the YAML wins and the row is corrected.
> **Maintained by:** each module owner fills the rows of their requirements: architectural consequence, ADR / invariant, component and verification method during SA; code and test evidence after implementation.
> **Last updated:** 2026-11-20

Cell conventions: `TBD` = not decided yet; `Proposed:` = from a document that is not yet accepted; `planned:` = named in the requirement's `verification` field but not written yet. Update the row in the same PR whenever the requirement's design, code or tests change. Test cases per criterion are in `verification-constraints.md` §7. Runtime Monitor names the metric from `requirements.yaml`; until a runtime component emits it, the offline tests compute it.

**Code and test evidence (2026-11-20).** The code below is implemented on branch `feat/implement-adr-001-008`, which is not yet committed or merged. Verdicts come from `docs/build-reports/REQ-001-010-build.md` §2: `uv run pytest test/offline` gave 172 passed, so every offline case below is PASS. Live and human checks are `NOT_RUN`. ADR-001 to ADR-008 and their invariants were accepted in SA Review (PR #22, 2026-11-18). All behaviour of REQ-001 to REQ-005 is behind the flags `task_contract_enabled` and `context_trimming` (default `False`), and REQ-008 is behind `search_fallback` (default `[]`).

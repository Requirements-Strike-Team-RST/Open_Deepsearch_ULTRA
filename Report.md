## 2. Project summary

Open Deep Research is an open-source research assistant. A supervisor divides a question into tasks. Researchers gather information and compress their findings. A final model uses those findings to write a cited report. We did not build a new research system. We improved the existing one where a user could not tell what had gone wrong, where results were lost, or where existing features were difficult to use.

We grouped the work into five broad areas: **defect repair, feature extension, stronger state management, deterministic decisions and modular design**. These are different ways of describing the work, not five disjoint sets of requirements. For example, reporting whether a run is complete, partial or failed fixes misleading output and adds a feature. It also requires explicit run state. Some improvements, such as early configuration checks and a consistent citation format, apply without a feature flag. Changes to task handling, compression recovery and search fallback are configurable so that we can compare them with the baseline.

The main design principle was to let the model propose answers and let code make the decisions that can be checked. A model may request that research stop. It cannot declare a question covered without a finding that passes the task contract. A model may propose a score. It cannot turn an invalid rating into a valid one. The same idea guided our development process: a coding agent could draft a change or report a result, but its claim was not itself evidence of correct behaviour or human approval.

## 3. Requirements: from observed problems to acceptance evidence

### 3.1 We started with the running product

Team members tried the upstream project before designing changes. Some problems were visible in the output. A run could end without showing that a researcher had failed. The compression and report prompts could also ask for different citation formats. We then used upstream issues to look for related problems. The issue descriptions were leads, not specifications. Members checked the behaviour against the version we were improving. This mattered because an upstream report could refer to another revision, and two bugs that look the same to the user can have different causes.

The delivery work gives a concrete example. We wanted to know whether a researcher error merely reduced the amount of evidence or stopped the research phase. The source and offline probes showed that the baseline could take the normal exit path after an exception. The final output did not reliably tell the user why research had stopped. That led to two separate questions: did each delegated task produce a result, and how should the entire run be described? We kept those questions separate in REQ-002 and REQ-004. A test that checks one task's status cannot by itself show that the report tells the truth about the run.

### 3.2 Two styles of requirement, with a shared format

The final requirements file has five entries typed `functional` and five typed `invariant`. In our discussions, we used functional requirements for behaviours the system must provide and invariants for properties that must remain true. This is not a strict split between new features and bug fixes. A functional requirement can repair existing behaviour. An invariant can require a new mechanism. Six of the ten requirements are marked `safety_relevant` in the file. Here that label concerns correctness boundaries, such as preventing a false completion decision. It does not mean that the project was audited for security.

We used **Given–When–Then** to make expected behaviour clear. For example, given a mismatched native search provider and research model, when research starts, the run must reject the configuration before calling a model or executing a search. Reviewers can challenge the input, the expected response or the timing without debating the wording of the entire feature. We also agreed that acceptance criteria should name their verification method. Some point to an offline test. Others need a live run or a person following the README.

For invariants, we added quantitative checks where they were useful. For example, the allowed count of lost delegations is zero. The allowed count of out-of-range scores is zero. The newest-turn preservation ratio is 1.0 in the targeted compression tests. Counts and ratios answer different questions. A count identifies a forbidden event. A ratio shows how often a property held over the cases measured. We did not choose a unit just to make the specification look precise. A threshold needs a scenario and a repeatable check. None of these offline targets is a claim about the rate of failures in production.

### 3.3 Consolidation and requirement volatility

Members first drafted requirements for their own problems. These drafts had different levels of detail and sometimes overlapped. We consolidated them into one YAML file with a shared schema. The consolidated set already contained REQ-001 through REQ-010. The later work on search fallback added and narrowed its **design**; it did not split REQ-008 out of REQ-007 after the requirements were approved.

The committed changes give a modest but useful measure of volatility. At the report snapshot, nine requirements were at version 1.1 and one was at version 1.2. The later change to REQ-007 corrected the tool name in C-004: the name to check is `tavily_search`, not `web_search`, which appears in metadata. This changed what a test should inspect, not what providers the product supports. Within the tracked YAML history, the ten-item scope stayed stable after consolidation. That does not mean the earlier drafts were stable or that all the design choices were clear. We had substantial change in interfaces and responsibilities after the requirement statements had settled.

We therefore distinguish **requirement change** from **design revision** and **test correction**. A new user obligation belongs in the requirements file. Replacing an overly complex design belongs in the decision records. A broken test fixture should be corrected against the existing acceptance criterion. Conflating the three makes it too easy to change a requirement just to fit a convenient implementation.

## 4. Architecture, integration and team coordination

### 4.1 Shared planning before separate module work

We used HackMD as a shared planning space. Members could read the same Markdown outline and comment on the templates and progress. The lead used it to make assignments and coordination visible. Members also used WeChat to announce progress and ask others to review work that touched their area. These tools served different purposes. HackMD helped us agree on what to do. Chat alerted people to changes. Git kept the reviewed artifact and its history. An informal update was not treated as a decision record or an approval.

Each member owned one module. We agreed on a common format for identifying architecturally significant requirements and comparing options using Attribute-Driven Design (ADD). We used the course's seven-step method as a guide. In the repository, the important result is the comparison: the quality goal, two or more viable options, the trade-offs and how the choice can be tested. We recorded the chosen design in an Architecture Decision Record (ADR). The eight final ADRs cover ten requirements. Related requirements share a decision where that makes ownership clearer. The number of ADRs is therefore not a coverage measure.

The comparison made it possible to reject a plausible approach for a concrete reason. For delivery, a single catch-all handler is short, but it cannot preserve sibling results reliably. A bounded queue with a separate result for each task makes it possible to test a failed researcher, a successful sibling and a task that never starts. For compression, an up-front estimate was possible, but it would add a model-dependent tokenizer. We chose to handle a token-limit error by removing the oldest removable whole turn. This kept the recovery logic small and testable. It also left a known cost: the initial oversized request can still be rejected.

### 4.2 Module review and integrated architecture review

Owners opened module draft pull requests and reviewed one another's designs. The module review was for findings and revisions. It was not the same as accepting the integrated architecture. Owners responded on the same branch so a reviewer could connect a concern to its fix. For instance, the [citations review](https://github.com/Requirements-Strike-Team-RST/Open_Deepsearch_ULTRA/pull/13) challenged duplicated citation instructions and checks that would not have had a clear pass or fail rule. The [context review](https://github.com/Requirements-Strike-Team-RST/Open_Deepsearch_ULTRA/pull/14) asked how a failed compression result could leave the researcher and still be interpreted correctly by its caller. The [evaluation review](https://github.com/Requirements-Strike-Team-RST/Open_Deepsearch_ULTRA/pull/15) challenged an import that would pull search-related code into evaluation.

After the module reviews, the integrator brought the branches together. This preserved each member's commits, but it also created a single place to resolve shared design decisions. The integrator reconciled colliding decision and test IDs. More importantly, they checked which module writes each field, which modules read it and what happens at each failure boundary. This is where ownership changed from a list of names to an enforceable part of the design.

One important case was the old delivery proposal for a node that ran twice. It needed a marker so that the first and second visits did different things. A missing or late marker could send the graph around a loop. The integrated design separated the steps. `check_research_outcome` decides whether writing a report is allowed. `final_report_generation` accounts for errors or truncation after writing starts. There is no need to route back through the same outcome node. Another decision gave `task_results` one owner for normal updates and a reset at the start of the next run. That avoids duplicate results and prevents old tasks from entering the new run's coverage calculation.

[PR #22](https://github.com/Requirements-Strike-Team-RST/Open_Deepsearch_ULTRA/pull/22) is the evidence for the integrated review. BroZhai and DopplerXD approved it, and it merged on 18 November. We use this PR to describe architecture acceptance. We do not count each module draft as a separate final approval. The two-reviewer merge rule also applied to the implementation. On [PR #24](https://github.com/Requirements-Strike-Team-RST/Open_Deepsearch_ULTRA/pull/24), NoPumpkinz and DopplerXD recorded the final approvals before the merge on 23 November.

### 4.3 Where coordination helped and where it concentrated work

Module ownership let six people work at once. Central coordination brought the designs, test names and implementation interfaces together. The first implementation pass was also coordinated centrally. That was useful for modules that depend on the same state. It made it possible to run the whole research workflow without waiting for several partially compatible changes. But the resulting PR covered all six modules. It asked reviewers to keep more context in mind at once and made it harder to isolate a change from the rest of the batch.

For the next iteration, we would keep a small shared change for the task result and its consumers, then use narrower review units for context, citations, search and evaluation where their dependencies allow it. We would also give each owner responsibility for maintaining their own status and evidence link. The lead could then focus on blockers that cross module boundaries. This would reduce dependence on one person keeping the whole progress board current. We do not have a reliable measure of how much time was lost to coordination delays, so we treat this as a lesson about ownership rather than a measured productivity result.

## 5. Human–agent workflow and quality assurance

### 5.1 Roles and handoffs

The intended workflow is: agree on the requirement, review the integrated design, write tests, review the test evidence, implement, verify and merge. The rule is not simply to plan before coding. Each handoff has a different question. Design review checks that the solution fits the requirement and other modules. Test approval checks that the test measures that behaviour. The final review checks the implementation, its evidence and known limits.

The four OpenCode roles have different permissions:

- **Architect** can draft and revise architecture documents. It does not write product code or tests. This is not the same as the built-in read-only Plan mode. We renamed the role after the built-in mode prevented approved design work from being saved ([PR #17](https://github.com/Requirements-Strike-Team-RST/Open_Deepsearch_ULTRA/pull/17)).
- **Test Author** writes offline and live tests from the accepted design. It checks why they fail on the baseline. A failure due to a broken fake or the wrong API is not useful baseline evidence. This role does not change the product code.
- **Build** implements the agreed design. It may run tests, but it must not change them to make the implementation pass. A suspected test defect goes back to test authoring, while a proposed change in behaviour goes back to design.
- **Verify** runs the checks and reports what passed, failed or could not run. It does not fix product code or tests. This gives the team a way to separate observation from correction.

These are limits on an agent session, not permanent assignments of students to roles. Humans decide whether to accept a change. The AI-use log and transcripts allow readers to see when a member spoke, when an agent proposed something and when a review exposed an error. A simulated peer review by a second agent was useful for challenging design. It did not count as a teammate's approval. The later correction pass changed both tests and source in one session, in that order. That helped recover the implementation, but it was not equivalent to independent approval of the corrected tests. Future corrections should preserve a review point between the two sets of changes.

### 5.2 What offline tests and CI established

Offline tests used fake models and tools to control the inputs and failures. They were useful for checking exact conditions: a premature completion request, an exception from one researcher while another succeeds, an incorrect citation source, or a rating outside the accepted range. We also ran the compiled graph in selected offline tests. A check of a function's return value does not prove that a graph routes the same way. That difference mattered when a static edge still sent a failed run to the report writer even though the outcome node itself returned an instruction to stop.

The GitHub workflow runs requirements schema validation, static analysis with Ruff and offline regression tests. All three checks passed on the final revision of [PR #24](https://github.com/Requirements-Strike-Team-RST/Open_Deepsearch_ULTRA/pull/24). The [offline CI job](https://github.com/Requirements-Strike-Team-RST/Open_Deepsearch_ULTRA/actions/runs/44899966336/job/136833595539) reported **172 passed**.

After PR #24, we added a fourth PR check: the [AI-use log gate](.github/workflows/ci.yml). It catches missing disclosures during PR review rather than at the end of the project. The [PR template](.github/pull_request_template.md) asks authors to declare `AI use: yes` or `AI use: no`. If they declare AI use, they add an entry to [`docs/ai-use-log.yaml`](docs/ai-use-log.yaml) and list its ID in the PR description, for example `AI-use log: AIU-028`. The check validates the log and compares IDs with the base revision. Citing or editing an existing entry does not count. A missing declaration, invalid log or missing new entry fails the check with instructions. Editing the PR description triggers a rerun. Dependabot PRs still validate the log but do not need a declaration.

We exercised 13 scenarios locally, including missing declarations, reuse of an old ID, malformed YAML and duplicate IDs. The hosted check and its enforcement as a required merge condition have not been verified. CI checks the declaration and the record; it cannot detect undeclared AI use or judge the quality of human supervision. Those decisions remain with reviewers.

### 5.3 What live checks added

Live runs exposed two different problems that the offline suite could not reveal. First, NoPumpkinz ran the citation test and found that it tried to execute an async graph through a synchronous entry point. The graph stopped before it could search or write anything. We changed both live tests to use one async helper and disabled clarification for unattended cases. The repair is in commit `150302f`; the [PR comment](https://github.com/Requirements-Strike-Team-RST/Open_Deepsearch_ULTRA/pull/24#issuecomment-7062017465) records the report and response. Getting past the async error did not prove that the citation test passed. A subsequent local attempt reached the model and then hit an account balance error.

Second, a manual DeepSeek and Tavily trial showed an output-budget problem. At the project's 8,192-token compression output setting, a separate reproduction showed a findings block cut off before it was complete. The graph correctly refused to count invalid output as evidence. With a local 32,768-token setting, a repeat run of the same question reached `covered` and produced a `complete` report. That was a practical mitigation for the tested configuration, not a universal fix. It was not proof that the two prescribed live queries passed. The difference between a model's input context window and its configured output budget is also important here. A large context window cannot prevent an answer from hitting a smaller output cap.

We kept those three statements apart: the async test harness was fixed; a manual run succeeded with a different budget; formal live and README review evidence was still incomplete in the records used here. This is why the merged implementation and the `approved` requirement labels in the YAML are not contradictory. They refer to different kinds of evidence.

## 6. Process quality, traceability and rework

### 6.1 How we resolved ambiguity

One of the clearest cases was [Discussion #19](https://github.com/Requirements-Strike-Team-RST/Open_Deepsearch_ULTRA/discussions/19). The search draft left questions open about unavailable tools, validation timing, model names and the old no-tools guard. During integration, the team discovered that the draft and the recorded answers were not aligned. The agreed design stops when no usable search tool exists. It checks before the first model or search call, checks native provider compatibility against an explicit list, and replaces the ineffective count of all tools with a search-capability check. The team recorded those decisions and brought the ADR, invariant, cases and configuration wording into line.

The fallback draft exposed a related ambiguity. It assumed that an earlier proposal for a structured MCP load result had been adopted. It had not. The integrated design distinguishes an unavailable fallback from a run with no usable search tool at all. It also says how to pass a query to the supported MCP fallback shape. This was a scope correction, not a new requirement. Without this reconciliation, a Build agent could follow both drafts faithfully and still implement the wrong combined behaviour.

### 6.2 How artifacts changed together

The [trace matrix](docs/architecture/trace-matrix.md) links the requirement to its ADR, invariant, enforcing code and verification method. It helped members see where another module was affected. A change to coverage, for example, can also change the final outcome, because the outcome reads the exit reason. A change to compression failure handling can affect delivery, because the task result crosses the researcher boundary. We used the matrix to make those connections visible. It was not a substitute for a project board or for reading the actual interfaces.

Co-evolution meant updating the artifacts that describe the same decision. When the two-pass outcome node was removed, the blueprint, delivery ADR and state ownership description had to agree on who writes the outcome and when. The verification cases then had to observe the real route through the graph. When the fallback design changed, its option comparison, ADR, runtime policy and test cases were updated together. When the live harness failed, a test-only commit corrected the harness, while the bug diary and PR comment explained why. No acceptance rule needed to change because the test had called the wrong interface.

We used automated checks for the parts that can be checked mechanically. Schema validation catches invalid fields and ID problems in the requirements specification. During integration and correction we also cross-checked document references and test names. That does not mean CI automatically proves a complete requirement-to-ADR mapping. A future check could start from changed requirements and report missing links to decisions, cases or test evidence. It should allow several requirements to share one ADR. Humans would still need to judge whether each link points to the right behaviour.

### 6.3 What the defect counts do and do not say

The first implementation pass reported **153 offline cases passed and 13 failed**. It attributed the failures to the tests. Rechecking the tests against the ADRs showed that the diagnosis was incomplete. Some fakes were wrong. Some assertions did not exercise the intended boundary. After the tests were corrected and expanded, **29 cases did not pass on the first implementation**. After the code corrections, the resulting suite had **172 passing cases**. These are three snapshots of different test or code states. The count of 29 is not a count of unique product defects. Nor can we calculate a defect rate from those totals.

A more useful trend is where defects were found. Module review exposed contradictory designs and unclear responsibilities before coding. Offline verification then exposed routing, state and error-handling problems. Real executions exposed provider limits and the live harness error. The [bug diary](docs/bug-diary.md) records examples by symptom and cause; the [build report](docs/build-reports/REQ-001-010-build.md) preserves the full correction pass. The evidence supports adding checks at the right stage. It does not support a claim that total defects fell over time in production.

### 6.4 What human oversight added

Human oversight mattered most when a green result or a plausible explanation did not answer the actual question. NoPumpkinz ran the live case instead of treating offline CI as a substitute. The search discussion gave the integrator something more reliable than an agent's summary of the team's decision. In evaluation, YANG Xinchuan required strict validation before a value could be converted. Otherwise a value such as `4.0` could turn into an integer and pass a check that claimed to accept only integers. In delivery and context, reviews asked which node actually received a failed task and which field carried it. A field listed in a document is not evidence that it reaches its reader.

Agents also found important problems, including defects found during the follow-up audit of tests and code. We distinguish those findings from human interventions. The human contribution was often choosing what to verify, challenging assumptions about ownership, or insisting on a real run. A good process makes both contributions visible without assigning every discovery to either the person or the tool.

## 7. Evidence to complete and priorities for the next iteration

We would make four changes in the next iteration:

1. Review the exact test revision before Build starts. Recheck it if the assertions change.
2. Exercise both live test entry points with a small compiled graph and fake models. That would catch API mismatches without a funded account.
3. Complete the prescribed live and README checks. Record the provider, flags, outcome, citations and any truncation for each live run.
4. Include evaluation code in CI lint and check trace links when requirements or code change.
